# T-030: 先頭エッジのレイテンシ低減（録音開始直後だけ再推論バジェットを短縮）※計測駆動・探索的

## 目的
- 定常状態の「ところどころのラグ」のうち、**録音開始から最初のテキストが出るまで**の体感を縮める。
- 現状 `minNewAudioSeconds = 1.5s` 固定のため、喋り始めても最短 1.5s ＋推論時間ぶん第一表示が遅れる。
- 録音開始直後の **先頭エッジだけ**バジェットを短くして第一表示を早め、その後は安定の 1.5s に戻す。

## 背景・前提
- これは構造的下限（Whisper オフライン型）の緩和策で、根治ではない。
  `docs/knowledge/realtime-budget-and-whisper-offline-limit.md` の方針内。
- 効果は環境依存（M1〜M5 で decode 速度差）。**必ず `[STT/timings]` 計測で副作用（バックログ）を確認**してから採否を決める。
- T-027 の教訓: 短いバジェットは pipeline > budget の局面で詰まりを生む。よって **常時短縮はしない**。
  先頭エッジ（窓がまだ短く decode が軽い局面）に限定する。

## 受け入れ条件
- [ ] 録音開始後の最初の1ステップ（または窓が短い初期数ステップ）に限り、`minNewAudioSeconds` を
      短い値（例: 0.6〜0.8s）に下げ、第一表示を早める。
- [ ] 一定条件（最初の確定が出た／窓が一定長を超えた等）で **1.5s 固定に復帰**する。復帰後は T-027 の挙動と同一。
- [ ] 最終テキスト・確定/未確定ロジック・無損失スライドに回帰がない（テキスト消失ゼロを維持）。
- [ ] `[STT/timings]` で、先頭短縮によりバックログ（pipeline が budget を継続的に超える状態）が
      悪化しないことを確認できる（人間が `/tmp/stt.log` で判定）。悪化する環境があれば短縮幅を保守的に。
- [ ] 効果が確認できない/悪化する場合は **入れない判断も可**（探索的タスク。実装はするが採否は計測で決める）。
- [ ] ビルド pass。

## 影響範囲（触ってよい範囲）
- `STTLocalApp/Speech/StreamingTranscriber.swift` のみ（バジェット制御ロジック）

## 制約・前提
- T-028 / T-029 と同一ブランチ。`transcribeStep` / `slideWindowIfNeeded` の既存構造を尊重し最小変更。
- 適応 budget（EMA/ピーク追従）は T-027 で撤回済み。**復活させない**。あくまで「先頭エッジの一時短縮→固定復帰」の単純ロジック。
- 暫定の判定に使った診断ログを追加する場合は、採否確定後に撤去できるよう局所化する。

## 完了の定義
- [ ] 全テストが pass / ビルド・lint クリーン
- [ ] 実機（人間）で第一表示が速くなり、かつ詰まりが悪化しないことを `[STT/timings]` で確認できる状態
- [ ] 採否の結論を progress / knowledge に記録（不採用なら理由を残す）
