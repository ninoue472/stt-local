# T-033: オーディオスレッド↔actor のデータ競合解消＋energy 経路を actor から外す

## 目的
- リアルタイムオーディオスレッド（タップコールバック）と `StreamingTranscriber` actor が、WhisperKit
  `AudioProcessor` の共有可変状態へ無ロックで並行アクセスしているデータ競合を解消する。
- あわせて、波形エネルギー更新の `Task→actor→MainActor` 3段ホップ（推論の重さに依存する）と、
  非構造化 Task の順序逆転（波形が一瞬巻き戻る）を、energy 経路を actor から外すことで同時に解消する。
- 2026-06-10 コードレビューで「唯一クラッシュ/メモリ破損の可能性がある真のデータ競合」かつ
  energy 系の Medium/Low 指摘を一箇所でまとめて解消できる Top3 として選定
  （`docs/reviews/code-review-2026-06-10.md`）。Swift 6 / Strict Concurrency 移行の最重要ポイント。

## 現状の問題箇所
- データ競合: `startRecordingLive` のコールバックはオーディオスレッドで `AudioProcessor.audioSamples` に
  append（内部ロック無し）。一方 actor 側は同じ `audioSamples` を読み（`StreamingTranscriber.swift:130,246`）、
  `purgeAudioSamples(keepingLast:)`（`:248`）の `removeFirst` で破壊的に変更する。append と read/removeFirst が
  無ロックで同一配列に同時アクセスしうる（purge は窓スライド時のみで稀だが真の競合）。
- 3段ホップ: タップコールバックが音声バッファ到来のたび（数十 ms 周期）に
  `Task { await self?.applyEnergy(energy) }` を生成 → actor 隔離の `applyEnergy`（`:259-263`）内で
  再度 `MainActor.run` へ。energy を推論ループと同一 actor に通すため、78-80 行のコメントが謳う
  「推論の重さに依存せずリアルタイム追従」が破られている。
- 順序逆転: コールバックごとの非構造化 Task は actor 到達順がスケジューラ依存で、古い energy が
  新しいものの後に適用され波形が巻き戻りうる（`:85-87`）。
- 関連: `Settings.shared` を actor 内から直接読む（`:67,144`）構造も Sendable 違反の温床
  （レビュー Medium）。録音開始前のスナップショット化で排除できる。

## 受け入れ条件
- [ ] 録音開始前に必要な設定値（modelName/language/budget 等）を MainActor で読み取り、Sendable な
      値型スナップショットとして `StreamingTranscriber.start()` に渡す。actor 内からの直接
      `Settings.shared` アクセス（`:67,144`）を排除する。
- [ ] energy 更新が actor を経由せず MainActor へ直接（または coalesce して）渡る。コールバックごとの
      非構造化 Task 乱立を廃し、最新値のみが反映される（順序逆転が起きない）。
- [ ] WhisperKit `AudioProcessor` の共有可変状態（`audioSamples` の append vs read/purge）への
      アクセス方式が、同期保証または排他のいずれかで明文化される。スレッドセーフでないことが確認された
      場合は read/purge とコールバックの並行前提をコメントで明記し、必要なら energy 取得もループ側へ寄せる。
- [ ] 波形のリアルタイム追従が推論の重さに依存しない（重いモデルでも波形が固まらない）ことを実機確認。
- [ ] テキスト消失・波形回帰が無い（録音開始/停止/再録音/モデル切替）。
- [ ] ビルド pass（`env -u CC -u CXX xcodebuild ...`）。可能なら `SWIFT_STRICT_CONCURRENCY=targeted`
      で新規警告が増えないことを確認（任意）。

## 影響範囲（触ってよい範囲）
- `STTLocalApp/Speech/StreamingTranscriber.swift`（energy 経路の再設計・設定スナップショット・purge/読みの並行前提）
- `STTLocalApp/State/Settings.swift`（スナップショット用の値型/読み取り API。必要最小限）
- 必要なら `STTLocalApp/App/AppDelegate.swift`（start() への設定受け渡し）と
  `STTLocalApp/State/AppState.swift`（energy の MainActor 受け口）

## 制約・前提
- 高リスク（並行性変更）。過去 T-013 と同様、**単独でリバート可能なコミット**に分け、実機確認を必須とする。
- 「波形＝入力モニタ、推論の重さに非依存」という既存設計（タップコールバック駆動）を**強化**する方向で、
  壊さない。
- `StreamingTranscriber` の actor 化・budget=固定1.5s・窓ハードキャップ（T-025/T-027）の挙動は変えない。
- WhisperKit `AudioProcessor` のスレッド安全性は外部依存。まず実装/ドキュメントを確認し、保証が無ければ
  「前提の明文化＋排他」で安全側に倒す（過剰なロックで波形追従を犠牲にしない）。
- ロジックは最小変更。UI レイアウト・配色は変更しない。
