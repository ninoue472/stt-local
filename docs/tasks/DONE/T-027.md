# T-027: 再推論間隔の最適化（適応budget 試行 → 固定1.5s）＋ 窓ハードキャップ

## 目的（当初）
- `minNewAudioSeconds`（再推論間隔=budget）を実測pipelineで自動調整し、全チップに適応させる（Issue #7）。

## 経緯（計測駆動で試行錯誤）
1. **適応budget(EMA)**: `budget = clamp(EMA×1.2, 0.8s, 4.0s)`、非対称EMA。
   → 速い局面でキビキビになる一方、**窓~8sのdecodeピーク(~1.1s)が下限0.8sを上回り周期的に詰まる**。
2. **窓のハードキャップ追加**: 連続発話で Whisper が 1 セグメントしか返さず確定が進まないと
   窓が暴走（実測 16〜40s/decode 最大3.3s）することを診断ログで特定。
   `slideWindowIfNeeded` で `bufferSeconds > hardCapSeconds(10s)` のとき最後のセグメントも
   昇格可（`minUnconfirmedToKeep=0`）にして窓を頭打ちに。→ 大暴走は大幅減。
3. **budgetをピーク追従に変更**: `peak = max(now, peak×0.9)`、下限1.2s。
   → 周期的詰まりは改善するが、**稀に窓が20s級に膨れる「間/無音や長い1句で transcribe 間隔が空き
   音声が溜まる」現象**は残った（budget起因ではなく、Whisperのオフライン構造＋実機の遅延ばらつき）。
4. **結論: 適応budgetを撤回し固定 1.5s へ**。固定の方が体感がスムーズで、1.5s は元の2.0sより速い妥協点。
   窓ハードキャップは有用なので残す。暫定診断ログ（[STT/diag]）は撤去。

## 最終的な変更（採用）
- `minNewAudioSeconds`: 2.0 → **1.5（固定）**。
- 窓ハードキャップ `hardCapSeconds = 10.0`（連続1セグメント発話の暴走防止）。
- 適応budget関連（EMA/ピーク保持/各定数）・暫定診断ログは**不採用/撤去**。
- `StreamingTranscriber.swift` のみ変更。T-025 の無損失スライドは不変。

## 受け入れ（実機計測）
- 通常 pipeline 600〜930ms と良好。窓は概ね頭打ち。
- 残課題: 稀に窓が20s級へ膨れ単発の詰まり（~2.8s）が出る。**budget調整では解消不可**。
  根本策は「軽量モデル(small)でdecodeを速くする」か「ストリーミング型エンジン（ネイティブ Speech）」。

## 知見 / 残課題
- **Whisper はオフライン(チャンク一括)モデル**で、リアルタイム化＝スライディング窓の再デコードが必須。
  窓が育つと decode が膨らむのは構造的限界。窓管理・budget調整は緩和策で、根治はしない。
  → `docs/knowledge/realtime-budget-and-whisper-offline-limit.md`
- 根治の方向性は別Issue化:
  - 軽量モデルで decode 高速化（Issue #8）。
  - ネイティブ Speech framework（ストリーミング・オンデバイス）をエンジン選択肢に（新Issue）。
