# T-032: prewarmWhisper の多重実行を直列化する（再試行/モデル切替の競合）

## 目的
- 再試行ボタン連打やモデル切替の連続操作で `prewarmWhisper()` が多重実行され、engine と
  モデル名が食い違う（`.ready` なのに実体が別モデル）競合を直す。あわせて各ロードが warmup 推論まで
  走ることによる CPU/メモリの二重消費を防ぐ。
- 2026-06-10 コードレビューで「ライフサイクル直列化の欠如」テーマの中核として Top2 に選定
  （`docs/reviews/code-review-2026-06-10.md`）。ここを正すと関連 Concurrency 指摘（start ロールバック・
  phase 逆転・既存 engine の nil 化）の堅牢化にも波及する。

## 現状の問題箇所
- `.retryModelLoad` は無条件に `prewarmWhisper()` を呼ぶ（`AppDelegate.swift:44-46`、再試行ボタンに
  デバウンス無し）。`.reloadModel` も `reloadModelIfPossible()` 経由で呼ぶ。
- `prewarmWhisper`（`AppDelegate.swift:63-110`）は複数の await（権限要求・`isModelCached`・`engine.load`・
  `warmupTranscription`）を持ち、進行中フラグ・世代トークン・Task の保持/cancel が無いため
  各サスペンドポイントで別呼び出しがインターリーブする。
- 各呼び出しが独立した `WhisperEngine()` を生成し、最後に `whisperEngine`/`streamingTranscriber`/
  `appState.phase` を上書きするが完了順序は非保証。遅い旧ロードが速い新ロードを上書きすると不整合。
- reload 経路にも `isModelCached`(`:81`) 前に phase が `.ready/.error` のままで2回目がすり抜ける
  ウィンドウがある。

## 受け入れ条件
- [ ] ロード進行中に `.retryModelLoad`/`.reloadModel` が連続発火しても、同時に走る `prewarmWhisper` は
      常に1つだけになる（進行中フラグまたは保持した Task の cancel で直列化）。
- [ ] 世代トークン（または現在 Task の同一性チェック）を導入し、**最新世代の結果のみ**が
      `whisperEngine`/`currentModelName`/`appState.phase` に反映される。旧世代は cancel または結果破棄。
- [ ] 反映後、`currentModelName` が指すモデルと実際にロードされた engine が必ず一致する。
- [ ] CPU/メモリの二重消費が起きない（重複ロード/重複 warmup が走らない）。
- [ ] 再試行連打・モデル連続切替で `.ready` 到達後に不整合が残らない（手動/可能ならテストで確認）。
- [ ] ビルド pass（`env -u CC -u CXX xcodebuild ...`）。

## 影響範囲（触ってよい範囲）
- `STTLocalApp/App/AppDelegate.swift`（`prewarmWhisper`/`reloadModelIfPossible`/通知購読の直列化・世代管理）
- 必要なら `STTLocalApp/State/AppState.swift` への小さな状態追加のみ（UI 大改変は不可）

## 制約・前提
- 既存の `.error` → `.retryModelLoad` 復旧導線は維持する（再試行で必ず最新意図のロードに収束）。
- 既存 engine の nil 化タイミング（レビュー Low 指摘: ロード失敗で前モデルも使えなくなる）は本タスクの
  直列化と密接だが、**ロード成功後に差し替える**改善は T-033 や別タスクと重複しない範囲で扱う
  （本タスクは「多重実行の直列化＋最新世代反映」に集中。nil 化改善まで踏み込む場合は受け入れ条件に明記）。
- start() 失敗時のロールバック（レビュー Medium）は別タスク。本タスクで巻き込まない。
- ロジックは最小変更。UI レイアウト・配色は変更しない。
