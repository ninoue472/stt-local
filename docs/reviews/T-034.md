# レビュー: T-034 AudioProcessor 内部バッファの頭打ち

- 対象 PR: #16（予定・実機確認後マージ）
- 実装: Codex / レビュー: Claude
- 起点: `docs/reviews/T-033.md` 要注意点1（T-033 由来のメモリ非有界成長）

## 実装の要点（`StreamingTranscriber.swift` のみ）

- 定数追加: `audioProcessorPurgeKeepSamples = 3 * WhisperKit.sampleRate`（保持 3s）、
  `audioProcessorPurgeThresholdSamples = 6 * WhisperKit.sampleRate`（しきい値 6s）。
- 録音タップコールバック内（`append` と同一オーディオスレッド）で、
  `audioProcessor.audioSamples.count > 6s` のときだけ `purgeAudioSamples(keepingLast: 3s)` を呼ぶ。
  → `audioSamples` は 3〜6s でオシレートし、約 6s ≒ 384KB に上限化。
- 定数はクロージャ前にローカルへ退避し、audio-thread クロージャで `self.` を踏まない。

## WhisperKit 内部の確認（Codex 報告・spot check 済み）

- `relativeEnergy` は `audioEnergy` を読む（`audioSamples` ではない）。
- `processBuffer` の energy も `audioEnergy.suffix(20)` ベース。
- `purgeAudioSamples(keepingLast:)` は `audioSamples` のみ削る（`audioEnergy` は触らない）。
- ⇒ `audioSamples` を purge しても波形ソース（`audioEnergy`/`relativeEnergy`）は壊れない。
  `audioEnergy` は非 purge だが 1 バッファ 1 Float（≒10/s）と極小で、メモリ上は無視できる。

## 受け入れ条件の検証

| 受け入れ条件 | 結果 | 根拠 |
|---|---|---|
| `audioSamples` が一定上限を超えて増え続けない | ✅(コード) | しきい値 6s 超で 3s へ purge。上限 ~6s で頭打ち。実機メモリ確認は人間 |
| 波形がこれまでどおり動作（purge で壊れない） | ✅(コード) | 波形ソース `audioEnergy` は purge 対象外。実機確認は人間 |
| 文字起こしに回帰なし（mirror/窓/clipTimestamps 不変） | ✅ | transcribe は `liveAudioBuffer` を使用。`audioProcessor.audioSamples` は transcribe 未使用 |
| データ競合を再導入しない（purge は callback=同一オーディオスレッド） | ✅ | コールバック内 purge。append と同一スレッドで直列化。actor からは触らない |
| ビルド pass | ✅ | `xcodebuild ... test` → **13 tests, 0 failures / TEST SUCCEEDED** |

## 設計評価

- **良い点**: 最小・低リスク。energy 経路（actor 隔離・load-bearing）と mirror/transcribe に一切触れず、
  「不要になった内部バッファの頭打ち」だけを同一スレッドで安全に実施。T-033 が解消したデータ競合を
  再導入しない（actor purge を避ける）点を明確に守っている。
- **しきい値の妥当性**: transcribe は `audioSamples` を使わないため、保持 3s は `relativeEnergy` が必要と
  する直近分（数百 ms）を十分カバー。3〜6s のヒステリシスで purge 頻度も低い。
